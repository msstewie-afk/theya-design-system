# Версии и changelog

Пакеты версионируются по semver через [Changesets](https://github.com/changesets/changesets). Версия и CHANGELOG ведутся для каждого пакета отдельно:

| Пакет | Что внутри |
|---|---|
| `@theya/shadcn` | компоненты, паттерны, стили |
| `@theya/tokens` | токены (Style Dictionary) |

`@theya/sandbox` (песочница) не версионируется.

Пакеты пока не публикуются в npm: приложения в `apps/*` берут их из исходников через `workspace:*`. Версия нужна, чтобы было видно, что и когда изменилось, и чтобы потом можно было опубликовать без перестройки процесса.

## Что считать major, minor, patch

Пока версии `0.x`, ломающие изменения поднимают minor, а не major (так принято в semver для нулевых версий). После `1.0.0` — как в таблице.

| Изменение | После 1.0 | Сейчас (0.x) |
|---|---|---|
| Убрали или переименовали компонент, проп, значение пропа, токен, экспорт; поменяли поведение так, что старый код работает иначе | major | minor |
| Новый компонент, проп, значение, токен; новая возможность без поломки старого | minor | minor |
| Исправление ошибки, доступности, стиля в рамках задуманного; правка документации и сторис | patch | patch |

Только тесты, сторис и документация (без изменений в том, что получает приложение) — changeset не нужен.

## Как добавить запись

Вместе с изменением, в том же коммите:

```
pnpm changeset
```

Команда спросит, какие пакеты затронуты и какой уровень. Описание — одна строка для человека, который обновляется: что изменилось и что ему сделать. Например: «Button: проп `type` переименован в `appearance`, замените в своём коде».

Если изменение затрагивает несколько пакетов по-разному, делайте отдельную запись на каждый пакет: текст записи целиком попадает в CHANGELOG каждого пакета, указанного в ней.

Файл появится в `.changeset/`. Его можно написать и вручную:

```md
---
"@theya/shadcn": patch
---

QueryBuilder: условия переносятся в столбец в узком контейнере вместо обрезки справа.
```

## Отчёт о публичном API

Публичный API `@theya/shadcn` описан в `packages/theya-shadcn/api/`. Там по одному файлу объявлений на каждую точку входа из `exports`: `api/ui/button.d.ts`, `api/blocks/workspace-layout.d.ts`, `api/lib/utils.d.ts`. В конце каждого файла перечислены значения пропсов по умолчанию. Отчёт генерируется, руками его не правим:

```
cd packages/theya-shadcn
pnpm api          # пересобрать спецификацию и отчёт
pnpm api:check    # падает, если отчёт устарел, и показывает, что изменилось
```

Если изменился компонент, проп, значение пропа, значение по умолчанию или экспорт, запустите `pnpm api` и закоммитьте `api/` вместе с изменением и записью changeset. Как читать diff в `api/`:

- **Строки только добавились** (новый проп, значение, экспорт) — minor.
- **Строка удалена или изменилась**, включая `// Component.prop = default`: тот, кто обновится, может сломаться. Пока версии 0.x, это minor, и в changeset пишем, что сделать при обновлении. Если поломку можно отложить, сначала идём через deprecation (ниже).

Комментарии и JSDoc в отчёт не попадают: правка описания не считается изменением API.

## Deprecation: как убирать и переименовывать

Ничего не удаляем и не переименовываем одним шагом. Порядок такой:

1. **Объявить.** Старое имя продолжает работать, рядом появляется новое.
   - На старый проп или экспорт ставим JSDoc `@deprecated` с указанием замены. Тег попадает в спецификацию и подсвечивается в редакторе.
   - В dev-режиме один раз выводим предупреждение: `warnDeprecated('Button type', 'use \`appearance\` instead.')` из `@theya/shadcn/lib/deprecation`.
   - Если устарел целый компонент, в его guidelines ставим `status: 'deprecated'` и `replacement`.
   - Changeset — minor, со строкой «Deprecated: …, замените на …».
2. **Подождать** хотя бы один minor-выпуск, чтобы приложения в `apps/*` успели перейти.
3. **Удалить.** Сейчас (0.x) это minor, после 1.0 — major. В changeset пишем, что именно убрано.

**Codemod.** Если замена механическая (переименование пропа, значения или компонента) и встречается в коде приложений больше пары раз, к шагу 1 прикладываем скрипт `packages/theya-shadcn/codemods/<версия>-<что>.mjs`. Скрипт переписывает использования сам, а в changeset пишем команду для его запуска. Инструмент (jscodeshift или ts-morph) выбираем, когда понадобится первый codemod.

## Как выпустить версию

```
pnpm version-packages
```

Changesets соберёт все записи, поднимет версии в `package.json`, допишет `CHANGELOG.md` в каждом пакете и удалит обработанные записи. Проверьте изменения, закоммитьте их, затем поставьте git-теги вида `@theya/shadcn@0.2.0`:

```
git add -A && git commit -m "release: version packages" && pnpm tag-release && git push --follow-tags
```

## Если понадобится публикация

Для проектов вне монорепо пакетам нужна сборка в `dist` (сейчас они отдают исходники). Решение отложено до первого такого проекта.
