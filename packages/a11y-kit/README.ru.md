# a11y-kit

Проверки доступности для дизайн-системы и продуктов на ней — из одного реестра: каждая проверка каждого слоя (код, компоненты в Storybook, страницы продукта, агент-ревьюер, люди), критерии WCAG 2.2, которые она подтверждает, её глубина и на чём она откалибрована.

English: [README.md](./README.md).

**Состояние (19.11.2026): шаги 1–3 плана сделаны** — реестр, калибровка axe, движок (`a11y-kit tree|auto|states|forced`) — и ревью изменений (ниже) из шага 4. Матрица (`build-a11y`) и очередь скринридера пока в Theya.

## Принцип: ничего на веру

Вердикт выносит детерминированный скрипт, а не модель: одинаковый вход — одинаковый JSON. Каждая проверка откалибрована на известных дефектах и чистых примерах (калибровочные сториз ДС, тест-кейсы W3C ACT, одно известное нарушение на правило axe), и калибровку человек запускает в своём терминале. Выборка находок каждого прогона уходит человеку, он отмечает «подтверждено» или «ложное», и точность каждой проверки видна в отчёте. Единственный слой с моделью — ревью изменений — помечен как мнение и сборку не роняет; его собственная точность считается по задачам, которые он заводит.

## Команды

Из пакета дизайн-системы (там, где `a11y-kit.config.mjs`):

```bash
node ../a11y-kit/bin/a11y-kit.mjs registry          # реестр и список проверок (EN + RU)
node ../a11y-kit/bin/a11y-kit.mjs registry --check  # ошибка, если устарели (в Theya: pnpm api:check)
node ../a11y-kit/bin/a11y-kit.mjs compare list.json # чек-лист другой команды против реестра
node ../a11y-kit/bin/a11y-kit.mjs calibrate-axe     # одно известное нарушение на правило axe, как axe запускается в CI (конфиг `axe`)
node ../a11y-kit/bin/a11y-kit.mjs contrast border background  # контраст двух токенов или цветов по WCAG, обе темы (конфиг `review.tokens`)
node ../a11y-kit/bin/a11y-kit.mjs review-precision  # как часто ревью изменений было право, по закрытым задачам (нужен gh)
```

`compare` принимает `[{ "id": "1.4.3-color-contrast", "sc": ["1.4.3"], "where": "ds" }, …]` (префикс критерия и `sc` необязательны; правило axe узнаётся по id после префикса) и показывает: строки, которые не правило axe и не проверка реестра (и что в реестре есть по их критерию); правила axe, которые запускаются только при явном включении (экспериментальные, устаревшие, выключенные); критерии, которые строка теряет, хотя axe связывает правило с ними; критерии WCAG 2.2 A/AA без строки; проверки реестра, для которых в списке нет строки.

## Ревью изменений

Агент (Claude) читает каждое изменение на соответствие WCAG 2.2 A/AA и сообщает то, чего не видят скрипты: ARIA-значение, которое валидно, но неверно; «исправление», которое улучшает контраст, но до нормы не дотягивает; клавиатурный путь, забытый рядом с обработчиком мыши; сочетание стилей, итог которого покажет только рендер. Его метод — [`review/agent.md`](./review/agent.md). Всё вокруг него детерминировано:

- `review-diff <from> <to> --out f` — изменение, только пути из `review.paths`.
- `review-context --out f` — из реестра: критерии, которые доказывают скрипты (их не ревьюим), остальные — с тем, что скрипты уже видят; принятые отступления ДС (`review.notes`), документы для чтения (`review.read`), команда `contrast`.
- `contrast <fg> <bg>` — агент называет только тот коэффициент, который посчитал здесь, по CSS самой ДС.
- `review-post` — проверяет findings.json агента до того, как что-то заводится: критерии AAA, доказанные скриптами и уровня продукта отбрасываются. Нарушение, не сверенное с кодом, или заявление о контрасте без пересчитанного значения понижается до «нужен прогон». Потом заводит по задаче на каждое нарушение и решение дизайнера (метка `a11y-review`, одна и та же находка — никогда дважды) и пишет один комментарий к коммиту или PR.
- `review-precision` — закрыта как выполненная = агент прав, как not planned = ошибся.
- `review-case`, `review-score`, `review-report` — калибровка самого ревью: каждый случай в `review.cases` — известное изменение (заложенный дефект на каждый критерий, который ревьюит агент, или изменение, по которому сообщать нечего) с ожидаемым ответом. 36 случаев Theya запускаются вручную `.github/workflows/a11y-review-calibrate.yml`; ответов агент не видит.

В Theya запускается на каждый пуш в main, который трогает компоненты, стили или токены (`.github/workflows/a11y-review.yml`), на подписке Claude владельца репозитория (секрет `CLAUDE_CODE_OAUTH_TOKEN`, создаётся `claude setup-token`). Задача агента может только читать репозиторий; задачи и комментарий пишет отдельная задача CI без агента.

3. Движок: tree, auto, states, forced переезжают сюда за адаптером ДС (конфиг: заголовок сториз → компонент, куда писать результаты). **Сделано:** `src/engine/`; `scripts/a11y-*.mjs` в Theya — обёртки. Доказано, что ничего не изменилось: старые скрипты и набор на одном Storybook дали побайтно одинаковые результаты по Combobox, Rating, SecretField и Tooltip во всех четырёх проверках, и набор проходит все 60 калибровочных сториз в каждой.
4. Чтение кода (2.1.4, 2.3.1, 2.5.1, 2.5.2, 2.5.7, 3.3.8), покрытие того, что прогон отрисовал (компоненты, ошибка, загрузка, disabled, expanded), режим страниц для продуктов (URL, проверки уровня страницы, находки привязаны к компонентам ДС через `data-slot`), выборка на ручную проверку (точность каждой проверки), ревью изменений (**сделано**, см. выше) и глубина, которой нет в списках: 2.2.1 таймауты, 2.2.2 пауза, 1.3.5 отсутствующий `autocomplete`, 1.4.1 состояние только цветом, 3.3.2 инструкции, пиксельная видимость фокуса в обычном режиме, неконтентный контраст, контраст текста там, где axe не может сказать.
