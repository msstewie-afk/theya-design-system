# Тесты

Все команды — из `packages/theya-shadcn`, при запущенном Storybook (`pnpm storybook`, порт 6008).

## Поведение и доступность

```
pnpm test-storybook        # светлая тема
pnpm test-storybook:dark   # тёмная тема
```

Каждая сторис: рендер, play-тест (если есть), проверка axe. Один файл: `pnpm test-storybook src/components/ui/button.stories.tsx`.

На ширине телефона: `THEYA_VIEWPORT=360 pnpm test-storybook` (и `:dark`; 375 — iPhone). Кроме play и axe, сторис падает, если страница прокручивается вбок. Сторис с тегом `desktop-play` пропускаются.

В продуктовой теме: `THEYA_BRAND=iris pnpm test-storybook` (и `:dark`). Подробнее и как проверить свою тему — в [PROFILES.ru.md](PROFILES.ru.md#проверка-темы).

Настоящим скринридером (вручную, WCAG 1.3.2 и 4.1.3): [packages/theya-shadcn/a11y/screen-reader-checklist.ru.md](packages/theya-shadcn/a11y/screen-reader-checklist.ru.md).

## Визуальная регрессия

Скриншот каждой сторис после её play-теста сравнивается с эталоном.

```
pnpm test-visual           # светлая тема
pnpm test-visual:dark      # тёмная тема
```

- Эталоны лежат в `packages/theya-shadcn/__visual__/<тема>/` и в git не попадают: рендер шрифтов отличается между машинами, поэтому сравнивать можно только на той, где эталоны сняты.
- Первый прогон на новой машине снимает эталоны, следующие сравнивают.
- Упавший снимок: картинка в `__visual__/<тема>/__diff__/` — слева эталон, справа новый снимок, посередине красным то, что изменилось.
- Изменение задумано — обновите эталоны этих сторис флагом `-u`:
  ```
  pnpm test-visual src/components/ui/button.stories.tsx -u
  pnpm test-visual:dark src/components/ui/button.stories.tsx -u
  ```
- Допуск — 50 пикселей: шум сглаживания проходит, перекрашенная граница маленькой кнопки уже нет.

Что тест делает сам, чтобы снимки не «плавали»:
- `prefers-reduced-motion`, CSS-анимации остановлены, курсор в полях скрыт;
- ждёт шрифты и все начатые загрузки картинок (включая предзагрузку Avatar);
- `Math.random` и `crypto.getRandomValues` перед каждой сторис дают одну и ту же последовательность.

Если в сторис есть то, что меняется само (живой таймер), закройте это маской — раскладка проверяется, содержимое нет:

```ts
parameters: { visual: { mask: ['[role="timer"]'] } }
```

Совсем исключить сторис из визуальной проверки: `parameters: { visual: { disable: true } }`.

## Режим высокой контрастности (forced colors)

В Windows High Contrast браузер заменяет все цвета на несколько системных и убирает тени и заливки. Правила для этого режима лежат в `src/styles/forced-colors.css` и в классах `forced-colors:` у Switch, Slider, Progress, Meter и Radio. Отдельный набор эталонов (`__visual__/light-forced/`):

```
pnpm test-visual:forced
```

Глазами — в Chrome DevTools: Rendering → Emulate CSS media feature forced-colors → active.

## CI (GitHub Actions)

Workflow `.github/workflows/ci.yml` запускается на каждый push в `main` и на каждый pull request. Если запушить ещё раз, пока прогон идёт, старый прогон отменяется.

1. **checks** (несколько минут):
   - типы;
   - `pnpm api:check`: спецификация, отчёт API и матрица доступности не устарели; у клиентских модулей есть `'use client'`; в компонентах только логические стороны (RTL); каждый `var(--…)` ссылается на что-то объявленное;
   - сборка песочницы `apps/sandbox` против пакета.
2. **storybook** (запускается после checks): статический Storybook, на нём
   - play-тесты и axe в светлой и тёмной теме;
   - визуальная регрессия в обеих темах.
3. **react-19** (после checks, параллельно со storybook): тот же код, но во всём репозитории принудительно стоит React 19 (пакет поддерживает 18 и 19, разработка и остальные проверки идут на 18). Проверяет, что React 18 не остался, затем типы, play-тесты и axe в светлой теме. Визуальная регрессия здесь не нужна — внешний вид от версии React не зависит.
4. **brands** (после checks, параллельно): по одной задаче на продуктовую тему, `iris` и `lime`. Play-тесты и axe в её светлом и тёмном вариантах, без визуальной регрессии.
5. **phone (360)** (после checks, параллельно): play-тесты и axe при ширине 360px в обеих темах и проверка, что страница не прокручивается вбок.

Эталоны для визуальной регрессии в CI свои. Их снимает Linux-раннер, а хранятся они в git, в ветке `visual-baselines` (`light/`, `dark/`, по одному PNG на id сторис). Не в `main`, и руками их не правят.

- **В `main`** (push, еженедельный прогон, ручной запуск) CI не сравнивает, а снимает заново: что в `main`, то и принятый вид. Визуальное изменение никогда не делает `main` красным и не требует перезапуска. Изменившиеся, новые и удалённые снимки уходят одним коммитом в `visual-baselines` с именем коммита `main`, который их вызвал (`visual: N change(s) from <sha>`). Этот коммит и есть ревью: GitHub показывает каждый PNG «до / после» (рядом, шторка, наложение). Сводка прогона («Visual changes: N») даёт на него ссылку и список сторис, в архиве `visual-changes` те же картинки «до / после». Стоит смотреть после каждого пуша, который менял вид, и особенно после того, который не должен был.
- **Отклонить изменение** — исправить код в `main`: следующий прогон снимет исправленный вид новым коммитом. Все прежние варианты остаются в истории ветки.
- **В pull request** CI сравнивает с `visual-baselines` и падает на изменении. В архиве `visual-diffs` — картинки «эталон | разница | новый снимок». Если изменение задумано, после слияния оно станет эталоном.
- Первый прогон (ветки `visual-baselines` ещё нет) снимает все эталоны и создаёт ветку.

**Упал `api:check`.** Изменился публичный API. Локально:

```
cd packages/theya-shadcn && pnpm api
```

Затем закоммитьте `api/` вместе с записью changeset (см. RELEASING.ru.md).
